### finding-1 [medium] 本地 OAuth 回调链路缺少 PKCE 且回调端口/路径可预测，授权码可被同机进程截获后独立兑换
- 描述: native/public client 的回环重定向 OAuth 流程未使用 PKCE：授权请求（MSAuthServer.java:70-76）无 code_challenge/code_challenge_method，令牌交换（MSAuth.java:213-219）无 code_verifier，client_id 是公开常量（IAS.java:55），回调是明文 http://localhost（MSAuthServer.java:82）且端口只从固定公开集合中挑选（IUtils.java:55-57），回调路径同样为硬编码常量。授权码因此是可独立兑换的 bearer 凭据：任何能观察到该码的同机进程（抢占/共享固定回环端口的本机监听者、读取浏览器地址栏或历史的其他软件）都可用同一 client_id 与 redirect_uri 直接换取 access_token+refresh_token，进而通过 XBL/XSTS/Minecraft 链路接管账号，无需任何客户端秘密。放大因素：回调监听绑定通配地址（MSAuthServer.java:377）；在 Windows 上 SO_REUSEADDR 语义下同机进程对同一端口的更具体 127.0.0.1 绑定可能与 0.0.0.0 绑定共存并优先接收浏览器回调（此平台细节为代码级推理，未联网/未实机验证）。修复方向：改用 PKCE（S256）并校验 code_verifier，绑定回环地址，避免低端口与可预测端口集合。

  3. 阅读 MSAuthServer.java:377 与 IUtils.java:248，确认 bind 使用 new InetSocketAddress(port)（0.0.0.0 通配地址）而非 InetAddress.getLoopbackAddress()。

### finding-3 [low] 回调一次性消费无鉴权且 /end 无 state 校验：任意本机进程或 DNS rebinding 网页可提前消费回调并关闭服务

### finding-14 [low] 本地回调 HTTP 服务为单线程串行处理，单个慢请求/不完整请求即可阻塞全部回调（缺 setExecutor/setSoTimeout）
- 描述: MSAuthServer.java:171 使用 HttpServer.create() 后从未调用 setExecutor(...) 或 setSoTimeout(...)，com.sun.net.httpserver 因此使用 sun.net.httpserver.ServerImpl$DefaultExecutor，在唯一的分发线程上内联执行处理器；而 "/" 处理器在 sendResponseHeaders/write 之后还同步执行 this.auth(uri)（MSAuthServer.java:224-253，含阻塞式令牌交换），"/end" 处理器同样同步读写。实测表明：任意一个未完成/慢速请求（或一个处理器内耗时请求）会串行阻塞所有其它回调请求，攻击者或恰好卡住的浏览器回调可导致合法回调长时间无法被处理，进而与已确认的 once 一次性消费逻辑叠加造成回调丢失；同时该服务绑定在 0.0.0.0，同网段主机在 loopback 检查前即可占用该单线程并制造持续排队。影响为本机一次性回调流程的可用性问题，故定级 low。
- 影响资产: （未关联）

  1. 把下列单文件 PoC 写入 %TEMP%\bindtest\SerialTest.java：HttpServer.create()（不调用 setExecutor/setSoTimeout）；createContext("/slow") 内先 Thread.sleep(2500) 再返回 200；createContext("/fast") 立即返回 200；createContext("/readbody") 执行 ex.getRequestBody().readAllBytes()；server.bind(new InetSocketAddress("127.0.0.1", 0), 0); server.start(); 用带 setSoTimeout 的原始 Socket 计量请求耗时。
  2. javac -d %TEMP%\bindtest %TEMP%\bindtest\SerialTest.java
  3. java -cp %TEMP%\bindtest SerialTest
  4. 读取输出：server.getExecutor() = sun.net.httpserver.ServerImpl$DefaultExecutor；BASELINE /fast alone = 375 ms；先发起阻塞 2500 ms 的 /slow，400 ms 后并发发起 /fast，实测 /fast 耗时 2125 ms（≈2500-400），证明串行。
  5. 再跑不完整请求变体：对 /readbody 发送 "POST /readbody HTTP/1.1\r\nHost: 127.0.0.1\r\nConnection: close\r\nContent-Length: 40\r\n\r\nABCD"（仅 4 字节体），2500 ms 后再补发剩余 36 字节；期间并发 GET /fast 实测耗时 2118 ms，同样被串行阻塞。
